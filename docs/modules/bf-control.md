# bf-control
**Status:** Partial — serves the public website, sign-in, the account page with add-a-device, and the node poller (all deployed to the web VM, 2026-11-10). Built and tested but **not deployed**: the admin panel (`/admin`, 2026-11-10, see "Admin panel" below).

## Overview
The control program. It is two things in one binary: with no arguments, a small web server for barely-free.com; with arguments, the admin tool (accounts, devices, kicks, the peer list).

### The website
A small web server for barely-free.com: a front page that says the service is a closed beta, how it will work, the two servers (status unknown), what is kept, and questions. It runs on the web VM behind a Cloudflare tunnel.

## Key details
- Code: `crates/bf-control/src/{lib,main,web}.rs` for the website. The pages are real files in `crates/bf-control/web/` (`index.html`, `404.html`, `cookies.html`, `site.css`, `favicon.svg`, and `fonts/` with two WOFF2 files and their licence) built into the binary.
- One handler takes every request (`web::page` decides, `web::secured` adds the headers), so even a 404 or 405 carries them: CSP `default-src 'none'; style-src 'self'; img-src 'self'; font-src 'self'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'` (`font-src 'self'` since the redesign, decision 027; a test pins the whole string), nosniff, `Referrer-Policy: same-origin`, HSTS, COOP and CORP same-origin, a permissions policy. No scripts and no outside resources (the donation links are plain links). Since 2026-11-10 (`specs/cookies.md`) the public pages have one form, the footer's theme buttons, so `form-action` is `'self'` (was `'none'`) and the referrer policy is `same-origin` (was `no-referrer`, which makes browsers send `Origin: null` on a form post; nothing is sent to other sites either way). The front page, `/cookies` and the 404 are `private, no-cache` (front page, `/cookies`) or `no-store` (404) and carry `Vary: Cookie`, because they differ by who is signed in and which theme is chosen.
- Routes: `/`, `/cookies`, `/check`, `/terms`, `/privacy`, `/abuse`, `/transparency`, `/help`, `/security`, `/.well-known/security.txt`, `/assets/site.css`, `/assets/fonts/geist-latin-wght-normal.woff2`, `/assets/fonts/bodoni-moda-latin-normal.woff2`, `/assets/fonts/bodoni-moda-latin-italic.woff2`, `/assets/fonts/OFL.txt`, `/favicon.svg`, `/robots.txt`, `/healthz`. Anything else is 404 (whatever the method); a wrong method on a real path is 405.
- **`/check`, "Am I on Barely-free?"** (2026-11-11, `research/vpn-check/RESEARCH.md`).
  - It takes Cloudflare's `cf-connecting-ip`, sent exactly once and a valid address, and compares it with the poller board's node addresses, whatever their health.
  - A match: "You are on Barely-free, through the <title>, <place> server", with the address sites see.
  - Otherwise: "You are not on Barely-free", showing the visitor's own address. That is `cf-connecting-ipv6` when Cloudflare's Pseudo IPv4 is on.
  - No board, no node, or no single good address: "This page cannot tell". It never guesses "not on".
  - `Cache-Control: no-store` and `Vary: Cookie`; nothing is logged or kept.
  - Linked from the front page's FAQ ("How do I know the VPN is on?") and the account page. The theme buttons return to it (`THEME_BACK`).
  - The answer is filled in at `<!-- the answer -->` in `web/check.html`, with titles HTML-escaped.
  - Limits: a server whose exit address differs from its agent address would read as "not on". IPv6 on the VPN would need the servers' IPv6 addresses here too.
- Listens on `BC_LISTEN` (default `127.0.0.1:18500`); `listen_address` refuses anything not on localhost.
- The page says "Closed beta" (with sign-up off; with sign-up open the badge reads "Full release · sign-up is open" and nothing says beta), marks features that do not exist yet as "Planned", and shows servers as "Status unknown" (never 0) until the poller has a reading.
- **Costs and funding** (`#funding`, with a "Funding" menu link): donations pay for the servers; one donation link out to `https://ko-fi.com/laouuu` (`rel="noopener noreferrer"`, labelled "Opens another site"); says a donation is a gift, not a purchase, no guarantee, no refunds, and what happens if the money runs out. No figures yet. The front page also has a **floating "Support me" button** (`.support-float`): a plain link in the corner to the same Ko-fi page, Ko-fi purple with white text, no script (Ko-fi's own widget would need scripts and outside loads, so it was not used). The only address on the site that points outside is that Ko-fi page (two links on the front page), and the tests insist on that. It is a link only, so the content security policy is unchanged. Spec: `specs/funding-page.md`; why Ko-fi: `research/donations/RESEARCH.md`.
- Tests: `web.rs` (pages, links all resolve, headers, a real-socket test) and `lib.rs` (listen address). Looked at in a browser at desktop and phone width.

## The control core (admin tool)
Spec: `specs/control-core.md`. Decision: [004](../decisions/004-list-from-database-and-time.md). Tables: [SCHEMA](../SCHEMA.md).

- `store.rs`: the SQLite database. Accounts, devices (lowest free address from `10.77.0.2`, device limit 3 per account, public key unique), kicks (a row each, for a time or until lifted), and `publish(now)`, which works out the peer list and its version. Every function that depends on time takes `now`; none reads a clock.
- `keys.rs`: new WireGuard key pairs (32 bytes from `/dev/urandom`, clamped, X25519 public key, base64). Checked against the RFC 7748 vector and `wg pubkey` on Toronto. The private key has no public field and is kept out of `Debug`.
- `cli.rs`: `run(args, db, now, out, err)` returns the exit code, so tests drive it without a process. `main.rs` passes it the real arguments, `BC_DB` and the clock; `tests/binary.rs` runs the real binary.
- Settings: `BC_DB` (database file, default `/var/lib/barely-free/control.db`), `BC_LISTEN` (website only). A setting that is set but not text is refused, never replaced by the default.

| Command | Does |
|---|---|
| `bf-control account add <label>` | Creates an account, prints its id |
| `bf-control account list` | Lists accounts: id, label, devices held of the limit |
| `bf-control device add <account-id> <name>` | Creates a device; prints its address, public key and, once, its private key |
| `bf-control device list` | Lists devices: id, account, address, active or kicked, name |
| `bf-control device remove <device-id>` | Removes a device: off the list, its address and slot are free again; the row and its kicks are kept |
| `bf-control kick <device-id> <length> [--by <who>] [--reason <text>]` | Kicks for `90s`, `30m`, `2h`, `7d` or `forever` (until lifted). The length is required |
| `bf-control kick list [<device-id>]` | Lists every kick (or one device's) with its device, who, why, when and whether lifted; removed devices included |
| `bf-control lift <device-id> [--by <who>]` | Ends every running kick on the device now, a removed device's too ([decision 012](../decisions/012-a-kick-blocks-adding-devices.md)) |
| `bf-control peers` | Prints the current peer list and its version as JSON |

Exit codes: 0 done, 1 refused or failed (the reason is on stderr), 2 not understood (usage on stderr). Results go to stdout. The private key goes to stdout only, once.

Rules: a label, name or `--by` is 1 to 64 characters without control characters or text-reordering marks (the bidirectional controls U+061C, U+200E, U+200F, U+202A to U+202E and U+2066 to U+2069, the line and paragraph separators U+2028 and U+2029, zero-width space U+200B, word joiner U+2060 and byte order mark U+FEFF; the zero-width joiner and non-joiner stay allowed because real scripts and emoji need them) (a label or name must also not start with `-`, so `--help` prints the usage instead of being stored); a reason is at most 200; an account holds at most 3 devices; an account with a kick in force on any of its devices, removed ones included, cannot add one ([decision 012](../decisions/012-a-kick-blocks-adding-devices.md)); a key must be canonical and unused; a kick needs a length above zero; lifting a device with no running kick changes nothing and says so.

Gotchas:
- `peers` records the version, so it is not read-only: running it after a change bumps the version once, and running it again changes nothing.
- **Open decision before the service uses the database:** which user owns it. The new file is mode 0600 and owned by whoever ran the command; today that would be root from a shell, and a `DynamicUser` service could not open it. `ProtectSystem=strict` also stops the service writing `/var/lib/barely-free`, and `deploy-web.sh` does not create the directory. The reviewer's suggestion: a static `barely-free` user, `User=` and `StateDirectory=barely-free` with `StateDirectoryMode=0700` in the unit, and the admin tool run as `sudo -u barely-free bf-control ...`. Not done, not decided. The default directory must exist and be writable by whoever runs the command until then.
- A file that already exists keeps whatever mode it has; only a file the program creates is made 0600.
- The private key is written out before the device is saved, in one transaction. If it cannot be written (closed pipe) or the process dies first, no device is kept and the command exits 1. A closed stdout (`>&-`) is the exception: Rust's standard library treats it as a successful write, so the device is kept and the key is lost; remove the device and run the command again.
- Labels and names are stored as typed (not trimmed) and may contain look-alike letters from other scripts. Direction-changing and invisible characters are refused (see Rules), but the future panel must still HTML-escape them.
- `kick` on a device that is already kicked for longer records the new kick and says it was kicked for the new length, though the longer kick still applies.
- The database holds labels and public keys, no secrets, but it is the only copy of the list version: back it up once it is deployed.
- Removing a device does not push anything. The list changes on the next `publish`.
- `device remove` keeps the device as history ([decision 005](../decisions/005-removed-devices-are-kept.md)): its kicks stay and `kick list` shows them; a kick still in force stays in force until it ends or is lifted ([decision 012](../decisions/012-a-kick-blocks-adding-devices.md)). Its address is free at once; its public key can never be used again. A database file from before this change has no `removed_at` column: delete it.
- A command that makes a new database file says so on stderr; if you did not mean to make one, `BC_DB` is wrong.
- The `-` rule for labels and names is in the command line only; `Store::add_account` accepts such text.

## Mail and secrets (sign-in, slice 1)
Spec: `specs/accounts-and-admin.md`. Nothing here is used by the website yet; it is the base for emailed sign-in codes.
- `secrets.rs`: the key file (`ControlKeys`): 64 random bytes as 128 hex characters, made once with mode 0600 (written under another name and hard-linked into place, so two programs starting together end with one file), refused if others can read it, never overwritten, never printed, kept out of `Debug`. It gives the email fingerprint, `HMAC-SHA256(key, lowercase(trim(email)))`, checked against `openssl`. The second key is for sign-in code checks (slice 2). `read_secret_text` reads any secret file under the same rules (owner-only mode, 4 KiB, text, a regular file; 0400 is fine, which is how systemd hands over a credential). **The fingerprint key cannot be rebuilt**: lose it and no stored fingerprint matches an address; back it up with the database.
- `mail.rs`: `signin_email(code)` builds the email from `mail/signin.html` and `mail/signin.txt` (the code must be exactly six ASCII digits; nothing else is ever put into the template); `check_address` (one plain ASCII address, no lists, display names, quotes, backslashes or spaces); the `Mailer` trait; `MailError`. The email has no images, no links and no tracking, one `<style>` block with a dark and a phone rule, and keeps the code out of the subject and the hidden preview line (inbox previews and lock screens show those).
- `resend.rs`: `ResendClient`, the real mailer. `POST {base}/emails` with a bearer key (header marked sensitive), `Idempotency-Key`, JSON with `html` and `text`; 10-second limit; no redirects followed; the base URL must be HTTPS (plain HTTP only for localhost or a loopback address); answers capped at 16 KiB. 2xx with an `id` = sent; 409 (`concurrent_idempotent_requests`, `invalid_idempotent_request`) = already sent; 429 `daily_quota_exceeded`/`monthly_quota_exceeded` = mail paused; other 429 and 5xx = one retry (same idempotency key); 401/403 = key or domain not accepted, no retry; 400/422 and unknown statuses = refused. The key is scrubbed out of anything that came back.
- `mailtest.rs` and `main.rs`: `bf-control mail-test <address>` sends the email with the sample code 482917 through the real client. Settings: `BC_RESEND_KEY_FILE` (default `/etc/barely-free/resend.key`), `BC_RESEND_URL` (default `https://api.resend.com`), `BC_MAIL_FROM` (default `Barely-Free VPN <noreply@barely-free.com>`). It needs no database. Exit codes 0 sent, 1 refused or failed, 2 not understood.
- `deploy/mail-test.sh <address>`: run by Lao on the Mac. Hidden key prompt, key in a private temporary file, file deleted when the script ends (also when stopped), never on a command line. Claude does not type, store or use keys.
- Tests: 14 for the client against a fake Resend (a real HTTP server on localhost), 7 for the email and addresses, 8 for the key file and fingerprints, 8 end-to-end for `mail-test` (the real binary against a fake), 5 for the script (the real script with a stand-in program). Mutation checks (follow redirects, no key scrub, three attempts, any HTTP host, key in the body, address lists, code in the subject) were each caught by a test. Also checked once against the real Resend with a dummy key: 401 "API key is invalid", mapped correctly (TLS roots and Resend's real error shape work).
- Gotchas: the web VM needs the system CA certificates (`ca-certificates`) because `reqwest` uses the platform's root store; `deploy/bf-control.service` no longer blocks outbound network as a whole (Resend publishes no addresses to allow-list); it denies only the internal ranges (decision 009); the Resend free plan is 100 emails a day, UTC; a Resend key pasted in a chat is exposed and must be revoked.

## Sign-in store (slice 2; built and tested, not connected to any page yet)
Spec: `specs/accounts-and-admin.md`. Tables: [SCHEMA](../SCHEMA.md), "Added in version 2". Code: `crates/bf-control/src/signin.rs` (methods on `Store`), helpers in `secrets.rs`. Every function that depends on time takes `now`; the address is only ever a keyed fingerprint.
- **Codes.** `request_code(keys, email_fp, ip_fp, now)` answers one of `Send { code_id, code }` (mail it), `Nothing` (no such account), `Limited` or `Paused`. The page for `Send` and `Nothing` must be the same. Order: purge, then the daily budget (90 sent emails per UTC day, or a Resend quota report, pauses everybody), then the limits (3 requests per address and 10 per network address in the last hour, counting every request whether or not an account has the address), then the account lookup. A new request deletes the address's old code. The code is six digits from `/dev/urandom` with the biased top of the range thrown away; the database holds only `HMAC-SHA256(code key, email_fp || code)`.
- **Mailing and the budget.** The store does not send mail. The web layer will hand `code` to the mailer in a background task and then call `record_mail_result(email_fp, Sent | Failed | QuotaExhausted, now)`; only `Sent` uses the budget, and `QuotaExhausted` pauses mail until midnight UTC.
- **Checking.** `verify_code(keys, email_fp, code, now)` is `Verified { account_id }` or `Bad`, and `Bad` is all anyone learns (no code, expired, used, wrong, wrong address, account gone). Five wrong tries end a code; a code works until exactly ten minutes after it was made; a right code is single use. Something that is not six ASCII digits is `Bad` without costing a try.
- **Sessions.** `create_session(account_id, now)` returns a cookie `<32 hex id>.<64 hex secret>` and a `csrf` token; the table holds the id and `SHA-256(secret)`. `session(cookie, now)` compares in constant time and is `None` for anything wrong or expired (60 days, absolute). `end_session` needs the right secret. An account keeps its newest ten sessions; expired ones are swept on each new code request or session. Debug output of a code request or a new session never shows the code or the secret.
- **Who has which address.** `set_email_fp(account_id, fp)` (one account per fingerprint; changing it lets the old address go) and `account_for_email_fp(fp)`. The command line for these is slice 3.
- **Known limits.** Someone who knows an address can spend a code's five tries and so stop that code working (a short denial of sign-in, bounded by the three requests an hour). A `Limited` answer is the same for known and unknown addresses by design, so it reveals nothing, but it also does not tell a real person how long to wait.
- **Tests.** 28 for sign-in, 16 for `secrets.rs`, plus the migration tests in `store.rs`. Checked with fifteen deliberate breakages (each caught): sixth try allowed, a code valid at exactly ten minutes, the hour window a second too long, limits off by one, an old code left behind, the budget off by one, the session secret stored in clear, a session valid at exactly 60 days, any secret accepted, sign-out without the secret, a used code working again, the code in `Debug`, eleven sessions kept, unknown addresses not counted. One of them found a gap in a test, which was strengthened.

## Sign-in pages (slice 3; built, tested and deployed)
Spec: `specs/accounts-and-admin.md`. Code: `app.rs` (the handlers and the startup), `form.rs`, `guard.rs`, `cookie.rs`, the templates in `templates/` (askama, which escapes everything; the pages share `base.html` and the site's stylesheet), and the routing in `web.rs`.
- **Routes.** `GET/POST /signin` (the address form; on success the browser goes on to `/verify`), `GET/POST /verify` (a page that is just the code box and names the address), `POST /signout`, `GET /account` (a minimal page: the label and a sign-out form; the devices list is slice 4). Anything else is the public site. A wrong method gets a 405 with `Allow`.
- **How the address gets to `/verify`.** In a cookie, `__Host-bf_pending`: the address as hex, `Path=/; Max-Age=600; Secure; HttpOnly; SameSite=Strict`, set when a code is asked for and cleared when it works. The web address stays plain `/verify`, the form on that page holds only the code, and the server stores no address. A version that put the address in the URL (`/verify?email=...`) was replaced: the address would sit in browser history and any URL log, anyone could craft a link that shows a convincing "code sent" page for an address of their choice, and a `+` in an address (`anna+news@...`) was read back as a space. The cookie proves nothing, since the code is still needed; an address in a form is ignored, and a missing or malformed cookie sends the browser back to `/signin`.
- **Same answer for everyone.** A code request for an address with an account and one without get the same status, headers and bytes, and the answer comes back before any email is sent (the mail goes in a task of its own, then its result is written down: only a sent mail uses the daily budget, and a Resend quota report pauses mail until midnight UTC). Too many requests is a 429 and paused mail a 503, the same for everyone. A wrong code gets one plain message whatever the reason, on the same `/verify` page, and that page says "If that address has an account, we sent a six-digit code to" for every address, so it never confirms one. What was typed is only ever shown again if it is a clean address, and then escaped.
- **Other sites cannot make a browser submit these forms.** Every POST needs `Sec-Fetch-Site: same-origin` and/or an `Origin` that is one of `BC_ORIGINS` (exactly, no `null`, with at least one of the two present); sign-out also needs the session's own form token. A form must be sent as `application/x-www-form-urlencoded`, at most 4 KiB, a field at most once.
- **The session** is the cookie `__Host-bf_session=<id>.<secret>; Path=/; Max-Age=5184000; Secure; HttpOnly; SameSite=Strict` (no `Domain`). Signing in again ends the session the browser held.
- **Headers.** Sign-in pages: `form-action 'self'` (the public pages keep `'none'`), `Cache-Control: no-store`, `X-Robots-Tag: noindex`, and `Referrer-Policy: same-origin`. **Not `no-referrer`**: with that policy a browser writes `Origin: null` on a form post, indistinguishable from a sandboxed page on another site, so every sign-in would be refused. Found with a real browser, not by the unit tests.
- **Off unless set up.** `web::serve_with(listener, Some(app), ...)` serves the pages; `None` leaves those paths as ordinary 404s. At start `main` builds the app from the settings below and, if anything is missing or wrong, logs `sign-in is off: <why>` and serves the website as before. Nothing is created by the web service: the key file is only read (the admin command line makes it), and the database is opened last, after every other setting checked out. In production, the dedicated `barely-free` user owns the state directory and the owner-only key files; outbound HTTPS is enabled for Resend.

| Setting | Default |
|---|---|
| `BC_KEY_FILE` | `/etc/barely-free/control.key` (read here, made by `account add --email` / `set-email`) |
| `BC_RESEND_KEY_FILE` | `/etc/barely-free/resend.key` |
| `BC_RESEND_URL` | `https://api.resend.com` (plain HTTP only for this computer) |
| `BC_MAIL_FROM` | `Barely-Free VPN <noreply@barely-free.com>` |
| `BC_OPEN_SIGNUP` | unset (closed); `1` opens sign-up, `0` closes it, anything else keeps sign-in off |
| `BC_NODE_BUSY_ONLINE` | `40`: devices online on a server (all its agents) at which "Closest to you" skips it; 1 to 100000, anything else keeps sign-in off |
| `BC_NODE_BUSY_LOAD` | `0.9`: a server's one-minute load at which it is skipped; above 0, at most 1000 |
| `BC_ORIGINS` | `https://barely-free.com,https://www.barely-free.com` (as a browser writes them: no slash, path, default port or capitals) |
| `BC_DB` | `/var/lib/barely-free/control.db` |

- **Open sign-up** (`BC_OPEN_SIGNUP`, off by default; spec `specs/open-signup.md`, decision [010](../decisions/010-open-sign-up.md)). `Store::with_open_signup(OpenLimits)` turns it on; `check_open_signup` reads the setting (unset or `0` closed, `1` open, anything else keeps sign-in off with a logged reason). On: `request_code` stores and mails a code for an address with no account too (its `mail_log` request row has `outcome = 'new'`); `verify_code` makes the account in the same transaction that uses the code up (`CodeCheck::Created`, label `member-<id>`, only the fingerprint kept). Two UTC-day caps, `OpenLimits::default()` = 60 requests for new addresses and 20 new accounts (any account made that day counts): past either, `CodeRequest::Full` (503 "Sign-ups are full for today", not written to `mail_log`, so it costs the person none of their 3 tries) and, if the last place went between asking and typing, `CodeCheck::Full` with the code left unused. Known addresses are never held by the caps. The pages follow the switch: `signin.html` and `code.html` take `open`, `web.rs` swaps the front page's closed wording through `OPEN_WORDING` (a test fails if `index.html` no longer holds a closed phrase), and `App::signup_open()` is read once at start (the pages are built while the store is locked, so asking the store would deadlock). Logs: `sign-up is open` at start, `sign-up: a new account was made`, `sign-up: today's room for new accounts is used up`; never an address, code or key. Tradeoff: on a day a cap is hit the "full" page is shown to new addresses only, so that page tells an address has no account.
- **Admin commands.** `bf-control account add <label> [--email <address>]` and `account set-email <id> <address>` turn the address into the stored fingerprint with the key file (made 0600 on first use, never overwritten) and refuse an address another account has. The address is not echoed and not kept.
- **Tests.** 28 for the pages and 4 for startup in `app.rs`, 11 + 5 + 4 for the form reader, origin check and cookie, 7 for the new commands, and end to end: `tests/signin_flow.rs` (a real socket), `tests/binary.rs` (the real program with sign-in off, on, half set up, and a bad origin), `tests/full_flow.rs` (admin command, real server, real Resend client, fake Resend). About fifty deliberate breakages (a dropped origin check, a sign-out without its token, a slower answer for known addresses, a code echoed, a mail result not written down, a session not replaced, and more) were each caught; one gap in a test was found and filled.
- **Gotchas.** The stylesheet is cached for an hour and the icon for a day (by browsers and by Cloudflare, which caches `.svg`), so every page links them as `/assets/site.css?v=<fingerprint>` and `/favicon.svg?v=<fingerprint>` (FNV-1a of the file; the server ignores the query). After any edit of `site.css` or `favicon.svg` the tests `every_page_links_the_stylesheet_by_a_version...` and `every_page_links_the_icon_by_a_version...` fail and print the new address to put in `web/index.html`, `web/404.html`, `web/cookies.html` and `templates/base.html` (both the `<link rel="icon">` and the header `<img>`). Learned 2026-11-10: the new icon was deployed but the live site kept showing the old one from Cloudflare's cache. The control key is created once and must be backed up with the database. A browser that has cached the stylesheet for `localhost` keeps showing it while developing; use another port.

## Node registry and poller (step 2, second part; built and tested, not deployed)
Spec: `specs/poller.md`. Decision: [008](../decisions/008-poller.md). Brief: `research/poller/RESEARCH.md`. Table: [SCHEMA](../SCHEMA.md) (`nodes`, schema 3).

- `nodes.rs`: the registry. `Store::add_node/nodes/enabled_nodes/node/set_node_enabled/remove_node`, `list_version` and `raise_version_floor`. A node is a name (`a-z`, `0-9`, `-`; it is the node's name inside its certificate, `<name>.agent.internal`, and the stem of its files), an `ip:port`, a title and a place for the site. No secret and no reading is in the database.
- `link.rs`: one node as the poller sees it. `read_files(dir, name)` reads `<name>.secret` (hex, at least 32 bytes, owner-only, small: the rules of the other key files) and `<name>.pem` (one or two certificates). `HttpsTransport` is a `reqwest` client built with `tls_certs_only` (only that node's root is trusted: no system or built-in root, checked in reqwest 0.13.5's source), `resolve` (the name goes to the registered address, so rustls verifies the name and sends it as SNI), HTTPS only, no redirects, no proxies, HTTP/1.1, 3 s to connect and 8 s in all, answers capped at 2 MiB (status) and 64 KiB. `Link` signs (`bf_common::sign`) with a time that is always later than the node's previous request (decision 007) and turns answers into `NodeReading` / `Pushed` / `LinkProblem`; the client addresses in a status are dropped when it is read.
- `poller.rs`: `Poller::pass` publishes the list once, then every enabled node runs at the same time with a 20 s deadline: read files, `GET /v1/status`, `PUT /v1/peers` only if the node's `desired_version` is not the list's version. A node that holds a newer version is flagged `Ahead` and sent nothing. Health: unknown until the first answer, "Not responding" after 3 failed passes in a row, online again after one success; a failed pass has no reading (never a count of 0); the whole board reads as unknown when the last pass finished over 60 s ago. Logs only on a change. `run` loops with `BC_POLL_SECS` (default 10, 2 to 300) and `poke()` makes the next pass come after at least 1 s.
- `web.rs`: the front page's Servers section is rebuilt on each request from the board (title, place, one of the five words of "Server status page" below, HTML-escaped); counts, load and reasons are not shown to the public. With no poller, or nothing on the board, the page is the file as it is.
- `cli.rs`: `bf-control node add <name> <ip:port> <title> <place> --protocol wireguard|amneziawg | set-protocol <name> <protocol> | list | enable | disable | remove | check <name>` and `bf-control list raise <n>`. `node check` makes the same signed request as the poller from the machine it runs on, prints the node's WireGuard public key, port, peer counts, load and how its list compares with the database's, and writes nothing.

- Deploy: `deploy/deploy-web.sh` installs `deploy/node-roots/*.pem` into the nodes directory; **you** run `deploy/set-node-secret.sh <name> "<ssh args for the node>" "<ssh args for the VM>"` once per node (the secret goes node to VM through your ssh and is never shown); then `bf-control node add ...` and `bf-control node check <name>` on the VM.

One opt-in test talks to the real nodes: `cargo test -p bf-control --lib real_nodes -- --ignored --nocapture` (2026-11-10: both nodes accepted the pinned root, answered a made-up secret with the agent's 404, and Toronto refused Dallas's root).
- Limits: a node that holds the same version number but a different list (only after a restored database and luck) is not noticed; the list is sent whole (about 120 bytes per device); one poller per database.

## Add a device on the account page (2026-11-10; deployed, waiting for the node secrets)
- `/account` lists the signed-in account's devices (name, tunnel address, date added, a Remove button) and, if the account is under its limit and a server is up, a form to name and add one. `POST /account/devices` makes a WireGuard key pair, adds the device (`add_device_with`, so nothing is kept if the file cannot be built), and answers with the device's `.conf` as text, as a QR code (inline `<svg>`, which the page's policy allows; `qrcode` 0.14.1 with only its `svg` feature) and as a `data:` download. **The private key is in that one response and nowhere else**: it is not stored, not logged, and a second send of the same form (`attempt` id, remembered in memory) gets a "was already made" page instead. `POST /account/devices/remove` removes one of the account's own devices (another account's id is a 404). The admin can still remove it; the kick stays in force until it is lifted. The account's other devices keep working: a kick takes only its own device off the servers. Both need the session, the form's own token and the same-origin check, like sign-out.
- `wgconf.rs`: the file (`[Interface]` with the key, `Address = 10.77.0.N/32`, `DNS` = the server's own resolver (see "Tracker blocking"; `1.1.1.1, 1.0.0.1` before it); `[Peer]` with the node's WireGuard key, `AllowedIPs = 0.0.0.0/0, ::/0`, `Endpoint = <node ip>:<its WireGuard port>`, `PersistentKeepalive = 25`), the percent-encoding for the download link, a safe file stem (`bf-<name>.conf`) and the QR code. `ClientConfig` has a hand-written `Debug` that leaves the private key out (like `KeyPair`), so a stray `{:?}` cannot print it; a test pins this for `{:?}` and `{:#?}`.

Caddy's HTTP/3 is disabled on 443 to free the UDP port; HTTPS remains available over TCP 443.
- Which node: since both protocols (below), the person picks a server and an app, and the agent with that server's title and that protocol must be online with a reading (its key and port come from its status, its IP from the registry). ## Admin panel (slice 5; built and tested, NOT deployed)
Spec: `specs/accounts-and-admin.md`. Code: `adminauth.rs` (the password, unlock and list queries, methods on `Store`), `app/admin.rs` (the pages), `templates/admin_*.html`, the gate in `web.rs`, the routes in `app.rs`, `cli.rs` (`admin ...`), `deploy/set-admin-password.sh`.

- **Two locks.** (1) A signed-in session whose account has `is_admin`, which only `bf-control admin grant <id>` sets (no web route can). (2) The admin password, asked for on `/admin` itself. A correct password unlocks that session for 30 minutes (`admin_until`); five wrong ones in a row lock the account's unlock for 15 minutes (the correct password also fails while locked; the lock belongs to the account, so more sessions do not give more tries); the page says the same thing whatever was wrong (wrong, locked, no password set). Argon2id (`argon2` 0.6.0: 19 MiB, 2 passes, 1 lane), at least 12 characters, at most 256 bytes; only the PHC hash is stored. Taking admin away (`admin revoke`), or setting a new password, ends every unlock of that account at once; `revoke` also forgets the hash and the lock. A new password does not sign anybody out, it only makes the next admin page ask for the password again.
- **Nobody else can tell the pages exist.** `web::handle` asks `App::admin_gate` before anything else: a request that is not from a signed-in admin (signed out, an ordinary account, a session that ran out, a database error: the answer is no) gets exactly the public 404 for all eight admin paths, and every other path under `/admin` (`/admin/`, `/admin/x`, `/Admin`) is the public 404 for everybody, admins included. Pinned by a real-socket test comparing the raw bytes (only `Date` is dropped) for GET, POST and HEAD, with no cookie, a junk cookie, an ordinary account, an admin, and an admin whose session has run out. A locked admin sees only the password page; the other pages send them to it.
- **Pages.** `/admin` (the password form; then the overview: accounts, devices and kicks in force, the servers with "unknown" and never 0 for a server with no reading, and the list version), `/admin/accounts` (every account: id, label, devices of limit, whether it has a sign-in address, admin, day made; a form to make an account with an optional address, kept only as a fingerprint), `/admin/devices` (every live device with its owner, address, day added, kicked or ok, and a Remove button), `/admin/kicks` (a form to kick a device by id with a required length, the kicks in force with a Lift button, a removed device's marked "(removed)", and the newest 100 others). Forms: `/admin/unlock`, `/admin/lock`, `/admin/accounts`, `/admin/devices/remove`, `/admin/kicks`, `/admin/kicks/lift`. Every one needs the same-origin check and the session's own token; every change but unlock and lock also needs an unlocked session. Kicks and lifts are recorded under the admin's account label; a removal, kick or lift asks the poller for a pass, so the servers have it in a moment. A label, a device name or a reason is text (askama escapes it).
- **Layout.** The pages use `main.wide` (64 rem) instead of the sign-in pages' narrow column: ids, dates and addresses never break, free text wraps, and on a phone each table scrolls sideways inside its own box (`.table-scroll`) and the page itself never does (measured at 375 px). Found in a real browser: in the narrow column the headers broke mid-word.
- **Setting the password (Lao runs it).** On the VM, once: `runuser -u barely-free -- /usr/local/bin/bf-control admin grant 1`. Then on the Mac: `deploy/set-admin-password.sh 1 root@<vm ip> -o Port=<ssh port>`. It asks twice with a hidden prompt (`IFS= read -rs`, so spaces and backslashes are kept as typed), sends the password through one pipe into `ssh -T` and `runuser -u barely-free -- /usr/local/bin/bf-control admin set-password <id>` on the VM, and never puts it on a command line, in a file or on screen. The id must be digits (it goes into the remote command). `admin set-password` refuses when standard input is a terminal (typed there it would echo), reads at most 1 KiB, and drops one line ending. Run it again to change the password; that also clears a lock, which is the way out of a lock-out (the panel says only "Try again in a moment").
- **Tests.** 33 for the pages in `app/tests/admin_pages.rs`, 23 for the store (`adminauth.rs`), 11 for the commands and the stdin reader (`cli_admin_tests.rs`), the gate in `web.rs`, and 11 that run the real script against the real binary with a stand-in `ssh` (`tests/admin_password_script.rs`). 133 deliberate breakages of the handlers, the gate, the routes, the templates, the script and the new fixes were tried; 130 were caught, and the other three change nothing a test could see (a fall-back for a database that fails between two queries of one request, the wording of a heading, how much is read before an over-long password is refused). The first run found real gaps, all filled: no test used an admin's session on the public paths, an expired admin session, a failing database, HEAD requests, or the real forms (a form without its token worked in every test because they posted by hand; `every_form_on_every_admin_page_would_work_in_a_browser` now reads them as the page gives them). Used in a real browser with a throwaway database and a fake mail endpoint: sign in, unlock, kick through the form, lock; desktop and phone, light and dark.
- **Second look in a real browser (2026-11-10, later, after the redesign).** Every page and form worked: unlock (wrong, then right), the overview counts, make an account with an address, kick by form, lift, remove a device, Lock; desktop and phone, light and dark, no sideways scroll on a phone (wide tables scroll in their own box). Improved from it, each test first: the menu marks the page you are on (`aria-current="page"`); each Remove and Lift button names its device for a screen reader ("Remove device 2, laptop"); each live device on the Devices page has a **Kick** link that opens `/admin/kicks?device=<id>` with the id filled in (only a query that is exactly `device=` and 1 to 12 digits fills anything); making an account with an address is now **one transaction** (`Store::add_account_with_email`, used by the page and by `account add --email`), so a failure never leaves an account without its address; and the log now says, by account id only, when someone unlocks, gives a wrong admin password, tries while locked out, has no password set, locks, makes an account or removes a device (journald: `journalctl -u bf-control`). Seven deliberate breakages of these were each caught.
- **Known limits (still open).** The Argon2 check runs while the store lock is held, which is bounded (five tries, only for a signed-in admin) but blocks the other requests for about a second per try. A password typed on a Mac and in a browser may differ if one side sends the composed form of an accented letter and the other the decomposed one, and the form's `maxlength` counts characters while the server limit is 256 bytes: use plain ASCII. The Kicks page reads every kick ever made and shows 100. There is no command that ends a stolen session (a session lasts 60 days, or up to a year if kept; `revoke` and a new password end only the unlock): "sign out everywhere" needs its own spec. Kicks are recorded under the admin's label, which is not unique (the log has the id).

## Cookies so the site remembers (2026-11-10; built and tested, NOT deployed)
Spec `specs/cookies.md`, research `research/cookies/RESEARCH.md`, decision `docs/decisions/011-kept-sessions-and-the-theme-cookie.md`.
- **Keep me signed in.** `/verify` has a tick box, unticked by default, "Keep me signed in on this device (uses a cookie)", which sends `keep=1` (anything else is no tick; a wrong code shows the page again with the box as it was). Unticked is unchanged: 60 days from sign-in. Ticked, the session (`sessions.keep = 1`, schema 4) is renewed when a **signed-in page** answers (`/account`, `/account/...`, the admin pages; not the sign-in pages, `/theme`, a wrong method or any answer of 400 or more): `Store::renew_session` gives it 60 days from now, at most once a day, never past 365 days from sign-in, and the answer sends the cookie again with `Max-Age` set to the time left. Renewal runs after the handler (`App::route`), so a sign-out has already ended the session and a sign-in has already replaced it, and a reply that sets the session cookie itself keeps its own (`with_renewed_session`). It is a plain read and then `UPDATE ... WHERE id = ? AND expires_at = <what was read>`, so it takes the write lock only when a renewal is due and never overwrites a row something else changed in between.
- **"Your account" on the front page.** `App::signed_in` checks the session cookie; with a live session the front page's Sign in button becomes `<a class="button" href="/account">Your account</a>`.
- **Theme.** Every footer (front page, 404, `/cookies`, every template page except the one-time device page) has three buttons, System, Light and Dark, posting to `POST /theme` with a hidden `back` path. `/theme` has the same-origin check and no session token (it changes nothing but colours); `light`/`dark` set `__Host-bf_theme=<value>; Path=/; Max-Age=31536000; Secure; HttpOnly; SameSite=Lax`, `system` clears it, anything else changes nothing; the answer is a 303 to `back` if it is one of `THEME_BACK` (`/`, `/signin`, `/verify`, `/account`, `/cookies`, `/admin`, `/admin/accounts`, `/admin/devices`, `/admin/kicks`), else to `/`. `web::themed` puts `data-theme="light"` or `"dark"` on `<html>` (one of two fixed words, never the cookie's text) and marks the pressed button (`aria-pressed`); `site.css` has `:root[data-theme=...]` rules, and the device's light setting applies only when there is no `data-theme`. Without the sign-in side (no `/theme`), the buttons are left out of the pages. The device page leaves them out on purpose: pressing one would leave the only page that shows the private key.
- **`/cookies`.** A static page listing the three cookies (what each does, when it is set, how long it lasts) and that Cloudflare sees them. A test reads the `pub const ..._COOKIE` names out of `cookie.rs` and fails if one has no entry, and another ties the lifetimes on the page to `SESSION_LIFETIME_SECS`, `KEPT_SESSION_MAX_SECS`, `CODE_LIFETIME_SECS` and `THEME_MAX_AGE_SECS`. Every footer and the tick box link to it.
- **Design (same day; superseded by the 2026-11-14 redesign below, which ended "system fonts only", "no motion" and "no gradient at all" but kept the bans on the AI look).** Lao said the site "looks super AI" (gradient headline, glow blobs, pill badges, tick chips, icon tiles, lifting cards, a purple lightning-bolt icon). It is now plain: system fonts only (the policy allows no font files), a serif for headings, monospace for technical bits, hairline rules instead of boxes, one green accent, square-ish corners, no animation. The Ko-fi "Support me" button is ink on paper (`var(--text)` on `var(--bg)`, Lao asked for it to match), and form field edges are at least 3:1 against their background (tests check the contrast of both colour schemes). The icon is new (a half-filled circle). Its address was not versioned at first, so after the deploy Cloudflare kept serving the old one; since then pages link `/favicon.svg?v=<fingerprint>`.
- **Tests and checks.** Store, app and web tests for each rule above (about 40 new); the full workspace suite passes (595). 23 deliberate breakages of the renewal, the tick, the theme route, the front page, the migration and the device page were each caught but one: removing the `expires_at = <what was read>` guard changes nothing a test can see (it only matters if the admin command line writes the same row in the same instant). Looked at in a real browser with a throwaway database and a fake mail endpoint: sign in with the box ticked (stored as kept), Dark from the footer on a light-mode device, the cookie page on a phone, light and dark, no sideways scroll. Reviewed twice (a code-reviewer agent and the separate Code review session); fixed from them: the theme buttons on the device page, the write lock taken on every request, the tick lost after a wrong code, renewal on pages that do not use the session, field edges under 3:1, no pressed state, `private` on the per-person pages.
- **Known limits.** A theme button press reloads the page, so anything half typed in a form on it (an address, a code, a password) is lost. Two requests at once on a renewal day can race: if a page that renews the old session answers after a sign-in that replaced it, the browser keeps the old (ended) cookie and is signed out; rare, and nothing is revived on the server. Once a version-4 database exists, an older binary refuses it (`NewerSchema`), so rolling back means restoring the database backup too. A kept session makes a stolen cookie worth more for longer; "sign out everywhere" and rotating the session id are follow-ups (`specs/cookies.md`, open questions).

## Closest to you (2026-11-11; built and tested, NOT deployed)
Decision [014](../decisions/014-closest-server.md); the design is the approved brief `research/trackers-and-closest/RESEARCH.md` (branch `feat/trackers`), built on `feat/dual-protocol`.
- **The form.** "Closest to you" (`server=auto`, constant `CLOSEST`) is the first Server option and checked; named servers follow, unchecked. The device page says "the server picked for you" when it was picked.
- **Where the person is.** `closest::from_headers` reads `cf-iplatitude` and `cf-iplongitude` before the form is read: each exactly once, a plain decimal number (digits, one point, a leading minus; no exponent, `inf`, `NaN` or `+`), latitude -90 to 90, longitude -180 to 180. Anything else is no location. The value lives in one local of `post_add_device`: never stored, logged or shown back. Cloudflare sends these only when the zone's Managed Transform "Add visitor location headers" is on; until the barely-free.com owner switches it on, everyone is "no location".
- **Where each server is.** Schema 6: `nodes.lat` and `nodes.lon` (both or neither, CHECKs on the ranges), set with `bf-control node set-location <name> <lat>,<lon>`; `node list` shows `at <lat>,<lon>` or `location not set`. The poller puts it on each board view (`NodeView.location`), read again every pass. A server takes the first location among its agents; set it on both.
- **The choice (`closest::pick`, `App::closest_server`).** Servers are grouped by title. A server is a candidate when it has an agent of the chosen app that is Online with a reading (the same test as a named choice, `choice_of`). Its devices online are the sum over all its agents' readings and its load the highest `load1`. Busy: online ≥ `BC_NODE_BUSY_ONLINE` (default 40) or load ≥ `BC_NODE_BUSY_LOAD` (default 0.9); no load reported is not busy. Busy servers are skipped; of the rest, those within 300 km (`EQUAL_KM`) of the nearest are equal and the less loaded wins (online, then load, then distance, then board order). A server with no location is infinitely far when the person has one. No person location: all equally near. All busy: the fewest online (then lower load). Great-circle distance by haversine on a 6371 km sphere.
- **Settings.** `BC_NODE_BUSY_ONLINE` (1 to 100000) and `BC_NODE_BUSY_LOAD` (above 0, at most 1000, a plain number) are read with the other sign-in settings (`AppSettings.busy`, `App::set_busy`); a bad value keeps sign-in off with the reason in the log.

## Alerts when a server stops answering (2026-11-11; built and tested, NOT deployed)
Brief: `research/alerts/RESEARCH.md`.

- **Down.** After 3 minutes down in a row (`DOWN_AFTER`), one email: "Toronto has not answered since 03:41 UTC."

- **Limits.**

  - Sending uses sign-in's Resend settings (`BC_RESEND_KEY_FILE`, `BC_RESEND_URL`, `BC_MAIL_FROM`).

## Login alerts (2026-11-12; DEPLOYED on the VM, Dallas and Toronto)
Spec `specs/login-alerts.md`, decision 023.
- **What is new.** A login whose (key, network) pair the website has not seen: the key's `SHA256:` fingerprint or `password`, and the address's `/24` or `/48` (`bf_common::logins::network`). The user and the server are not part of the pair.
- **Sources.** On every server a root timer, `bf-logins.timer` (`deploy/bf-logins.sh`), writes the `Accepted` lines of the last 15 minutes and `ssh-keygen -lf` of the `authorized_keys` files into `/var/lib/barely-free-logins` (group `bf-logins` reads it). Each agent's status carries those logins; `link.rs` keeps only safe ones (`link::safe`: plain user name, a fingerprint of the right shape, key name cleaned and cut to 80). The website reads the VM's own from the same folder (`BC_LOGINS_DIR`), through `bf_common::logins::from_files`; `deploy-web.sh` puts the `barely-free` user in `bf-logins`, installs the timer and runs it once before the website restarts. A logins file older than 5 minutes is logged once and read as nothing; a missing one is nothing.
- **`logins.rs`.** `Known` holds the pairs from `/var/lib/barely-free/known-logins` (`BC_KNOWN_LOGINS`): `news()` gives the logins of unknown pairs and remembers them, `learn()` adds without alerting, `save()` merges with the file (another writer's pairs are kept) and writes it whole, 0600, through `<file>.new` and a rename. With no file, the first look learns silently. `vm_logins(dir, now)` reads the VM's files. `run()` is `bf-control logins learn`.
- **`alerts.rs`.** `LoginWatch::step` collects every agent's and the VM's logins, merges the two agents of one server (same server, time, user, address, key), and turns the news into `Alert::NewLogin`. `look_all` puts down, back and login news in one email under the same daily cap; past it, every line is logged. The subject names the servers ("New login to Dallas", "New logins to Dallas, Toronto"); login lines come first, then the advice to remove the key, then any down news. An agent with no `logins` (older, or its journal unreadable), the VM file and the known file are each logged once when they fail and once when they are fine again.
- **Settings.** On only when the down alerts are on (address file and Resend key). If the known file cannot be read: "login alerts are off: <why>", and the down alerts carry on.
- **Seeding.** `deploy/seed-known-logins.sh` (from the Mac) pipes 90 days of `Accepted` lines from the VM, Dallas and Toronto into `bf-control logins learn` on the VM as the website's user, then `systemctl try-restart bf-control`. Nothing is written on the Mac.
- **Tests:** `logins.rs` (learning, news once, a restart, bad lines, merging on save, the VM files fresh and stale, the command), `alerts.rs` (wording and escaping, the shared email and subject, two agents of a server as one line, the cap, logged once), `link.rs` (unsafe logins dropped one by one), `tests/logins_script.rs` (the real `bf-logins.sh` with a stand-in `journalctl` and the real `ssh-keygen`, its unit and timer, the group and order in both deploy scripts), `tests/node_protocol_scripts.rs` (the agents' drop-ins), `tests/seed_logins_script.rs` (the real script with a stand-in `ssh` and the real `bf-control`).

## Backups (2026-11-11; built and tested, NOT deployed)
Spec: `specs/backup.md`. Decision: [016](../decisions/016-nightly-encrypted-backup.md). Brief: `research/backup/RESEARCH.md`.
- **`backup.rs`, `bf-control backup <file>`.**
  - Opens `BC_DB` read-only with a 10-second busy wait and runs `VACUUM INTO` into a new 0600 file. The folder must be closed to group and others, and an existing file is refused.
  - Since 2026-11-12 the copy leaves out the short-lived sign-in records (`backup::SIGN_IN_RECORDS`: `mail_log` and `login_codes`, with their email and network-address fingerprints). It empties them in the copy and vacuums it again, with temporary data in memory, so no deleted row lingers. An older database without those tables is copied as it is. The privacy policy relies on this: the copy is kept 30 nights next to the key that made the fingerprints, and an IPv4 fingerprint can be reversed with that key.
  - Checks the copy with `integrity_check` and prints `backup written to <file>: schema version <v>, <n> bytes`. On any failure the file is removed.
  - Never makes or upgrades a database.
- **`backup.rs`, the status.**
  - `parse_status` reads the status file the script writes: five `name=value` lines (`finished`, `file`, `sent`, `failed`, `error`), each exactly once.
  - `status_line` turns it into the admin overview's "Backups" line, warning (`.note.warn`) when there is no file, the file can't be read or understood, the run failed, or it is older than `STALE_AFTER` (36 h).
  - The path is `BC_BACKUP_STATUS` (default `/var/lib/barely-free/backup-status`), carried in `AppSettings.backup_status`.
- **`deploy/bf-backup.sh`**, installed as `/usr/local/lib/barely-free/bf-backup.sh`, run by `bf-backup.service` from `bf-backup.timer`.
  - Refuses a recipients file that is missing, empty, writable by group or others, or has a line not starting `age1`. Refuses a targets file with a line that isn't `bf-backup@<IPv4>`.
  - Copies, packs (manifest, `control.db`, `control.key`), encrypts with `age -R` and sends with `ssh -F /dev/null -i ... -o StrictHostKeyChecking=yes -o BatchMode=yes <target> put <name>`.
  - Writes the status file atomically. Exits 1 if anything or any target failed.
- **The unit** keeps every sandbox setting of `bf-control.service` (`tests/backup_units.rs` compares them), adds `AF_UNIX`, and may write only `/var/lib/barely-free`. Its plain files live in `RuntimeDirectory=bf-backup` (0700, tmpfs).
- **On each node**, `deploy/bf-backup-receive` is the forced command of the `bf-backup` user's one key. `deploy/node-backup-receiver.sh` installs it. That script checks `sshd -T` (one line per `allowusers`/`denyusers` entry) and exits 2 if sshd would keep `bf-backup` out.
- **`deploy/setup-backup.sh`** sets up the VM; `--finish` pins the nodes. **`deploy/restore-backup.sh fetch|put`** restores.

- **`/robots.txt`**: `User-agent: *`, `Allow: /`, one `Sitemap:` line. No `Disallow` (the private pages are `noindex`, and Google never sees a noindex on a page it may not fetch) and no `admin` (the site answers `/admin` like any unknown path; a line would announce it). Tests refuse both.
- **Canonical links.** Each indexable page has one `<link rel="canonical" href="https://barely-free.com{path}">` in its head (the front page: `https://barely-free.com/`), equal to its sitemap address. `www.barely-free.com` answers 200 with the same page, so this is what settles the duplicate in code.
- **`/check` is `noindex`** (a meta tag, and still crawlable) with no canonical and no sitemap entry; its body is the visitor's own address.
- **Link previews.** Each indexable page's head has `og:site_name` ("Barely-free"), `og:type` (`website`), `og:title` (the page's `<title>`), `og:description` (its meta description), `og:url` (its canonical) and `twitter:card` (`summary`). No image yet (a 1200×630 share image is a separate later step; `Page.body` is a `&str`, so serving a binary needs a small change). `/check` and the 404 page carry none. The front page's `OPEN_WORDING` has a pair for `og:description` too, so the description and the preview change together when sign-up opens (`the_front_pages_two_descriptions_change_together_when_sign_up_opens`).
- **`WebSite` data, front page only.** `<script type="application/ld+json">` with `@type` `WebSite`, `name` "Barely-free", `alternateName` `["barely-free.com"]`, `url` `https://barely-free.com/`. No description and no operator name. It is a data block, not a program: a page served with the real policy showed a console error for a control inline script and none for this block (2026-11-12). `runnable_scripts` (in the `web.rs` tests) counts every other `<script`, and the old "no scripts" tests use it, so a script that runs still fails them.
- **Titles and descriptions** are held distinct (one each per page), descriptions at most 160 characters raw, and there is no `keywords` meta.
- **A new page file in `web/` must be decided about**: `every_page_file_is_in_the_sitemap_or_kept_out_on_purpose` scans the folder and fails until the page is in `INDEXABLE` (and the sitemap) or in `KEPT_OUT`.
- **The "outside address" check** (`the_only_addresses_outside_this_site_are_ko_fi_and_the_public_source_repository`) now counts only the exact host `https://barely-free.com` or `https://barely-free.com/...` as this site; a longer name that starts with it, `www` and plain `http` still count as outside.
- Not done on purpose: IndexNow, Organization markup, hreflang, `lastmod`, any analytics. See the brief for why.

## Uptime history and the maintenance note (2026-11-14; built and tested, NOT deployed)
Spec `specs/status-history.md`, decision [026](../decisions/026-uptime-history-and-maintenance-note.md), brief `research/status-history/RESEARCH.md`, tables in [SCHEMA](../SCHEMA.md) (schema 7).

- `nodes.rs`: `Node.note`, `Store::disable_node(name, note)` (checked by `check_node_note`, 1 to 100 characters, `StoreError::BadNodeNote`), `set_node_enabled` clears the note either way; `SCHEMA_7`. `store.rs`: `SCHEMA_VERSION = 7`, `upgrade_to_7`.
- `cli.rs`: `node disable <name> [--note TEXT]` (the note is free text, so a leading dash is fine) and `node list` shows `disabled (note)`.
- `uptime.rs`: `Store::record_uptime(now, passes)` (one transaction, an upsert per server into the current hour's row), `prune_uptime(now)` (older than 90 days), `uptime_summary(now)` (30 days, 720 hours, by title and place, servers with nothing counted left out), `tenths(up, down)` (rounded down; 1000 only with no down time; no overflow), `Availability`, `Uptime`.
- `status.rs`: `availability(&[NodeView])` (working when some agent is online, down when the word would be Down, nothing for Being fixed and Status unknown; checked against `servers` for every mix of one to three agents), `Server.fixing_note` (the first note among the agents being fixed, only while the word is Being fixed), `answer(snapshot, busy, now, uptime)` adds the note lines, an "Uptime" list (`99.8% over 12 days`, `no history yet`, never a count) and a sentence saying what is counted.
- `poller.rs`: `NodeView.note` (set by `switched_off` from the node's row), `Board::uptime()` / `set_uptime` (kept across passes, not part of `Snapshot`), and after every pass `record_uptime`: the pass's availability is added, the table is pruned on the first pass of each UTC day, the summary is refreshed on the board. A failure is logged once per change ("cannot keep the uptime history: ...", then "the uptime history is being kept again") and never stops the pass.
- Why the summary is refreshed every pass and not once a minute: it is one query over a few thousand rows, and it needs no timer. Why "over N days" and not a date: no date code needed.
- Tests: `nodes.rs` (migration 6 to 7, the note rules), `uptime.rs` (counting, windows, pruning, rounding, a property test that it never rounds up), `status.rs` (note and uptime rendering, availability against the word), `poller.rs` (note on the board, recording, being fixed counts nothing, two agents count once, pruning once a day, a failed write is logged once), `cli_nodes_tests.rs`, and an end-to-end test in `tests/binary.rs` with the real program (the percentage appears, a note set with the real command shows and clears, the history survives a restart).
- Limits: nothing is counted while the website is down or restarting; an outage shorter than the poller's three failed passes is not seen; a renamed server splits its history (it is keyed by title and place).

## Sending the sign-in codes (planned, step 2)

## The redesign (2026-11-14, decisions 027 and 028; deployed 2026-11-14)
Architecture: brief `research/redesign/RESEARCH.md`, spec `specs/redesign.md`, decision 027 ("Hairline"). Look: `research/redesign-editorial/RESEARCH.md`, spec `specs/redesign-editorial.md`, decision 028 (the editorial direction). Merged into `dev` as `e80f7af` and deployed 2026-11-14.
- **Stylesheet.** One file for every page. Order: the `@font-face` rules (Geist; Bodoni Moda upright and italic, whose `unicode-range` leaves out the hyphen, dashes, minus and underscore because its own are invisible hairlines; then the fallback faces "Geist Fallback" on Arial and "Bodoni Fallback" on Times New Roman, upright and italic, sized to the real fonts' measured width and ascent); the colour tokens (the dark ones in the first `:root` block, the light ones twice, in `@media (prefers-color-scheme: light) { :root:not([data-theme]) {...} }` and `:root[data-theme="light"]`, kept identical by a test); base and type (`--serif` for headings, `--sans` for the rest, the spaced small capitals as `.label` and friends); buttons (a square of the accent, an ink sweep drawn by `::before` and moved by `transform`); header and phone menu; the narrow, wide and legal pages; the front page; forced colours and print; and last, one `@media (prefers-reduced-motion: no-preference)` block that holds every animation, transition, scroll behaviour, view transition and the header's hiding rule (a test splits the file there and fails if any of those words appears before it). Inside it only transform and opacity move and nothing is endless (a test reads every keyframe and transition); scroll-driven rules sit under `@supports (animation-timeline: ...)`, the header's hiding under `@supports (container-type: scroll-state)`, the phone menu's fade under `@supports selector(:popover-open)`.
- **Fonts.** `Page.bytes` carries a file of bytes (`font_bytes`); the three font paths are in `page()`'s match. The WOFF2 files are named in `site.css` as `url("/assets/fonts/<name>?v=<fingerprint>")`; every page preloads Geist and Bodoni Moda upright, the front page also the italic; tests tie each to the files' FNV-1a fingerprints. Bodoni Moda's files are Fontsource 5.3.0's `opsz` files narrowed with `fontTools.varLib.instancer` to `{"opsz": (24, 96), "wght": (400, 600)}` (recipe and reasons in the research addendum). To change a font: replace the file, run the tests, copy the new fingerprint into `site.css`, then re-stamp the pages. Geist Mono is no longer served (its address is a 404) and its file was deleted.
- **Header and footer** are written out in every page file and in `templates/base.html` and held equal by `every_public_page_has_the_same_header_and_footer`. The header is `<header class="top">` with the inline logo mark and the name, a menu button (`popovertarget="menu"`, drawn as the word "Menu" or "Close" by CSS) and `<nav id="menu" popover>`: Why, How it works, Servers, Privacy, Questions, Help (phone panel only), Source code, Account, Get started. The source link and the account link are picked out by `a[rel]` and `a[href="/account"]` (their markup is fixed by tests and by `ACCOUNT_NAV`). The footer is a bare `<footer>` with a brand block, the three link columns under small capitals, the owner line, "This site runs no scripts and loads nothing from other sites." and the theme form. The device page still empties the `nav`, `site_links` and `theme_form` blocks. Each page's two `theme-color` lines are its themes' grounds (a test).
- **"Get started".** `HEADER_CTA` is the menu's text link; `for_visitor` (fixed pages, `/check`, `/status`) and the front page's own branch drop it for a signed-in visitor, `without_sign_in` drops it where there is no sign-in side, and the account, admin and unlock templates empty `{% block cta %}`.
- **Front page.** Nine sections: `hero`, `why`, `how`, `nodes`, `features` (the specification sheet, a `<dl class="spec">`), `privacy`, `funding`, `faq`, `closing`; `privacy`, `funding` and `faq` must stay bare `<section id="...">` tags because other tests split on them. The hero's picture is `<svg class="hero-art">` (the mark: a ring and a filled half), positioned so the screen's edge cuts it; the headline is three `<span class="line"><span>...</span></span>` clipping boxes with one `<em>`, each line with its own delay rule. `OPEN_WORDING` swaps the closed wording for the open one. Server names appear only on the live board (the specification says "Two to start with").
- **The map.** `status::map(&[Server]) -> Option<String>` is unchanged (decision 027): a 640 by 360 frame centred on the servers, a whole-degree grid, hemisphere letters, one `<g class="place">` per located server. On the front page `#nodes .board` cancels the section's side padding, so the plate runs the full width; its place names are set in Bodoni from the stylesheet. On `/status` it stays in the column.
- **Retention.** `<ol class="retention">`: six rows, each a number and a hairline `.b1` to `.b6` whose width is `log10(minutes)` over the longest's; `front.rs` computes every number and width from the code's constants.
- **Looking at it.** The pages are plain files, so the quickest look is a static server that serves `web/` with the production policy (no script is needed); for the server-filled parts (the map, the signed-in pages) run `bf-control` against a throwaway database (`account add --email`, `admin grant`, `admin set-password` from a pipe) with `BC_RESEND_URL` pointing at a small fake server that records each request body and answers 200 with `{"id": "..."}`, `BC_ORIGINS` set to the preview's own address and `BC_RESEND_KEY_FILE` at mode 0600; the six-digit code is in the recorded body. A screenshot taken right after a scroll or a click can be one frame old; a browser pane that is hidden draws no frames at all, which delays the header's scroll state by one gesture and aborts page transitions: take a screenshot to force a frame, or read `scrollY` and computed styles.
- **Known limits.** The header hides only in Chrome and Edge 144 and later. Firefox before 159 and Safari before 26 get no scroll-linked moments; Firefox gets no page transitions. The map shows only servers that have coordinates. Layout shift on localhost was 0.012 (all from `<body>`'s default margin, which the same harness reports as 0.574 for the old build); on the live site it was 0. Cloudflare injects two scripts (an inline one and its Insights beacon) that the policy blocks; they show as console errors only.
